# Actor Component Framework: Consumer API

## Purpose and scope

This document describes the framework surface used by game/application code on the client and server: declarations, setup, state access, commands, events, and transport adapters. It intentionally does not describe framework internals.

The API below records the current design direction. Code snippets are illustrative where a signature is still undecided; unresolved items are listed at the end so they can be reviewed incrementally.

## Core model

- Consumers declare the actor types and component types their application supports.
- The server is authoritative for actor/component lifecycle and server state.
- Clients do not create/delete actors or add/remove components. Clients send domain commands, such as `shoot`, to a component on an actor.
- Client state and server state are distinct contracts. Client state is populated and updated by handling server-to-client events.
- Static declarations are distinct from runtime values: `ActorDeclaration` versus `Actor`, and `ComponentDefinition` versus `Component`.
- A consumer may keep declarations in the application or in a shared package. Client and server may use the same declarations while being initialized in separate projects.
- The consumer supplies the transport adapter. Handlers and application code publish/consume typed framework events rather than depending on a specific network library.

## Component contracts

A component has:

1. `ClientState`, read by client code and updated by client event handlers.
2. `ServerState`, authoritative and updated by server command handlers.
3. A client-to-server command map. Each key is a command name and its value is that command's payload type.
4. Typed server-side events and corresponding client-facing event payloads. Event names are local to a component and are namespaced when published (for example, `health:changed`).
5. Server command handlers and client event handlers.

Consumers use explicit TypeScript generic arguments for component declarations. TypeScript types are the data contract; runtime schemas are not part of the current design.

```ts
type HealthClientState = {
  value: number;
};

type HealthServerState = {
  value: number;
  lastUpdatedBy: string;
};

type HealthCommands = {
  set: { value: number };
  add: { amount: number };
};

type HealthServerEvents = {
  changed: { actorId: string; value: number; lastUpdatedBy: string };
};

type HealthClientEvents = {
  changed: { actorId: string; value: number };
};

const healthComponent = declareComponent<
  HealthClientState,
  HealthServerState,
  HealthCommands,
  HealthServerEvents,
  HealthClientEvents
>("health", {
  createServerState: (serverContext) => ({
    value: 100,
    lastUpdatedBy: serverContext.systemName,
  }),

  commandHandlers: {
    set: (data, context) => {
      context.state.update((current) => ({
        ...current,
        value: data.value,
      }));

      context.eventBus.publish("health:changed", {
        actorId: context.actor.id,
        value: data.value,
        lastUpdatedBy: context.state.value.lastUpdatedBy,
      });
    },
    add: (data, context) => {
      // Command handling is server-side. Handler details remain a consumer concern.
    },
  },

  clientEventHandlers: {
    changed: (event, context) => {
      context.state.update((current) => ({
        ...current,
        value: event.value,
      }));
    },
  },
});
```

The snippet shows the intended shape, not a finalized signature. In particular, the exact generic ordering, handler context types, and the placement of server-to-client event projection logic remain open.

### State initialization and updates

- A component declaration provides a server-state factory. The factory receives server context and is used to create initial authoritative state.
- When an actor is created or a component is added, the caller may provide state overrides. Overrides are shallow-merged with the factory result; omitted top-level fields retain their factory values.
- There is no client-state factory in the current design. Client event handlers initialize and update client state from server events.
- State is exposed read-only to consumers. Handlers use a reducer-style state API, conceptually `state.update(current => nextState)`, rather than mutating state objects directly.

### Actor declarations

`defineActor` declares an actor type and the components it has by default. The list is a set of defaults, not an allowlist; additional registered components may be added dynamically on the server.

```ts
const playerActor = defineActor("player", ["health", "weapon"]);
const bulletActor = defineActor("bullet", ["projectile"]);
```

Actor IDs are generated by the framework. Actor creation and optional state overrides are server-side operations.

## Client layer

The client is initialized with the application's actor and component declarations. It does not expose lifecycle mutation methods.

```ts
const clientApi = createClient({
  actors: [playerActor, bulletActor],
  components: [healthComponent, weaponComponent, projectileComponent],
});
```

The object-based setup above is a readable sketch; whether setup takes an object or positional arguments is not finalized.

### Actor and component access

The client exposes flat lookup methods. `getActors` applies its predicate to the current actor set and returns a snapshot array of live handles; call it again to re-filter after changes.

```ts
const actor = clientApi.getActor("player-0");
const players = clientApi.getActors((candidate) => candidate.type === "player");

const health = actor?.getComponent("health");
const currentHealth = health?.state.value;
```

Client actor/component handles are live views: their read-only state reflects current client state. Component handles can send only commands declared by their component:

```ts
actor?.getComponent("weapon")?.send("shoot", {
  position: { x: 1, y: 2, z: 3 },
  rotation: { x: 0, y: 0, z: 0 },
});
```

Sending a command does not create an actor or component and does not return a request/response result. The client observes resulting state through server events.

### Client event handlers and side effects

Declared client event handlers update client state from the client-facing event payload. Consumers may also subscribe to events for application side effects, such as updating UI state:

```ts
clientApi.on("health:changed", (event) => {
  healthRef.current = event.value;
});

clientApi.off("health:changed", onHealthChanged);
```

`on`/`off` are the proposed subscription shape. Exact listener payloads and whether all event categories are exposed through this same surface remain to be specified.

## Server layer

The server is initialized with the same declaration sets and server-specific configuration/context. Client and server can initialize these independently when deployed as separate projects.

```ts
const serverApi = createServer({
  actors: [playerActor, bulletActor],
  components: [healthComponent, weaponComponent, projectileComponent],
  context: serverContext,
});
```

The configuration shape is illustrative. In particular, the exact way server context is supplied has not been finalized.

### Server actor and component access

The server exposes actor lookup and filtering as well as lifecycle methods:

```ts
const actor = serverApi.getActor(actorId);
const players = serverApi.getActors((candidate) => candidate.type === "player");

const result = serverApi.createActor("bullet", {
  projectile: { speed: 12 },
});

if (result.success) {
  const bullet = result.actor;
  bullet.getComponent("projectile")?.state.update((current) => ({
    ...current,
    speed: 14,
  }));
}

serverApi.deleteActor(actorId);
```

The intended operation result shapes are:

```ts
type CreateActorResult =
  | { success: true; actor: ServerActor }
  | { success: false };

type LifecycleResult =
  | { success: true }
  | { success: false };
```

Actor handles support dynamic component membership:

```ts
const actor = serverApi.getActor(actorId);

actor?.addComponent("health", { value: 50 });
actor?.removeComponent("health");
```

`deleteActor` takes an actor ID. `removeComponent` takes a component type/name. The current design has no declaration-level lifecycle predicates: command handlers perform application checks and call lifecycle APIs only when appropriate. No denial side-effect event has been requested.

The exact return shape of `addComponent` needs reconciliation: it was first expected to return a component handle, while the later uniform lifecycle-result choice suggests `{ success: true } | { success: false }` for add/remove/delete and reserves the returned handle for successful actor creation.

### Command handlers

Component command handlers run on the server and receive typed command data plus context for the relevant actor/component, state updates, the server API, and event publication. A handler can implement domain logic and then call server lifecycle methods. For example, a `shoot` handler may create a bullet actor.

The client sends only declared domain commands. It does not send actor/component lifecycle commands. Exact handler context members and the command transport signature are still open.

## Events

Events are typed by name and payload. Component event names are declared locally and published with a component namespace, for example:

```ts
eventBus.publish("health:changed", {
  actorId,
  value: 75,
  lastUpdatedBy: "system",
});
```

Application/framework-wide event names can also be published, for example:

```ts
eventBus.publish("actor:created", { actor });
```

The event bus is intended to accept only names and payloads present in the registered event contracts. The server publishes server-side event data. The server-side transport listener then converts that data to the corresponding client-facing event payload before sending it through the consumer's transport adapter.

Handlers are transport-agnostic: they publish events on the event bus and do not know which clients receive them. The consumer-provided transport adapter handles routing and delivery. Server handlers explicitly publish lifecycle and domain events; lifecycle events are not automatically emitted by the framework in the current design.

The current event model therefore distinguishes:

- **Server event data** — typed data published by server code; may include server-side state.
- **Client event data** — typed, client-facing payload handled on the client.
- **Projection** — conversion from server event data to client event data, performed between the server event bus and client transport.

The precise type declaration and the location of the projection function have not been settled. Server event payloads may contain authoritative/private state, so the client-facing projection must be deliberate.

## Transport setup

The consumer provides transport sender/listener adapters so it can choose its networking infrastructure. The framework's transport integration connects client commands to the server and server events to the appropriate client-side event handlers. Server handlers publish to the event bus rather than invoking transport APIs.

An earlier API sketch used a transport initializer returning lifecycle controls:

```ts
const transport = initializeTransport(eventBus, {
  sender,
  receiver,
});

transport.start();
transport.stop();
```

The exact `Sender`/`Receiver` types, client/server initializer signatures, and routing contract are not finalized. Multi-room routing and broadcasting to multiple clients are expected to be handled by the transport adapter, but the required adapter interface remains open.

## Decisions still open

1. **Server-to-client projection:** Where is the projection declared—on the component declaration, in the transport adapter, or in a separate projector?
2. **`addComponent` result:** Does success return the new component handle, or only a lifecycle success result?
3. **Declaration signature:** What is the exact argument shape and generic ordering for `declareComponent`, `defineActor`, `createClient`, and `createServer`?
4. **Event contracts:** How are component-local server event payloads paired with client-facing event payloads, and how are global events such as `actor:created` declared?
5. **Handler context:** Which exact typed helpers are available to command and event handlers, including the server API, state API, and event bus?
6. **Subscriptions:** Are `on`/`off` available on both APIs, and which server-side versus client-facing events do they expose?
7. **Transport contract:** What are the exact sender/receiver methods and how does the adapter select recipients, rooms, and broadcasts?
8. **Actor creation inputs:** What is the precise typed shape for selecting default components and providing per-component server-state overrides?
